## 이 프로젝트를 시작한 이유

서점 후기 앱들은 대부분 "별점 먼저, 글은 나중"이었습니다. 그런데 제가 실제로 책 이야기를 나누고 싶을 때 원했던 건 반대였습니다 — **먼저 생각을 글로 정리하고, 필요하면 그 위에 사진이나 책 정보를 얹는 방식**이었습니다.

텍스처북은 그 가설 하나에서 출발한 '텍스트 퍼스트' 북 커뮤니티입니다. 제목·본문 작성이 항상 첫 단계이고, 미디어 첨부와 책 카드(ISBN) 태깅은 선택 사항으로 설계했습니다.

| Frontend | React 18 + Vite, Tailwind CSS |
| Backend / DB | Firebase (Authentication, Firestore, Storage) |

## 핵심 기능

- **이메일 + Google 소셜 로그인**, 로그인 상태 전역 관리 (Context API)
- **텍스트 퍼스트 에디터**: 제목/본문 우선, 미디어·책 카드는 선택
- **스포일러 블라인드**: 체크 시 본문·미디어가 블러 처리되고 클릭해야 해제
- **4종 감정 리액션** (맛있어요/심오해요/이야기해요/안 맞아요) + 대댓글
- **유저 구독(팔로우)** 시스템
- **신뢰도 기반 칭호 시스템** — 활동 지표에 따라 "마스터 테이스터", "북 소믈리에" 자동 부여
- **마이페이지(비주얼 서재)** — 획득 칭호와 작성/좋아요한 글을 갤러리로 정리

## 🔥 트러블슈팅 — AI와 함께, 하지만 AI에게만 맡기지 않은 과정

이 프로젝트에서 가장 많이 배운 구간은 사실 화면을 만드는 단계가 아니라 **"왜 안 되는가"를 추적하는 단계**였습니다. 아래는 실제로 겪은 순서 그대로입니다.

### 1) "흰 화면만 떠요" — 진입점이라는 개념을 처음 체감하다

AI가 만들어준 코드 조각들을 그대로 폴더에 옮기고 `npm run dev`를 돌렸더니 빈 화면만 나왔습니다. 처음엔 코드 자체가 잘못된 줄 알았습니다.

원인을 하나씩 좁혀가며 알게 된 사실은 세 가지였습니다.

1. `index.html`이 컴포넌트 파일(`PostDetail.jsx`)을 **직접** 불러오고 있었다 — React는 컴포넌트를 곧바로 실행할 수 없고, 반드시 `ReactDOM.createRoot`로 마운트하는 진입점(`main.jsx`)을 거쳐야 합니다.
2. 그 진입점 파일 자체가 존재하지 않았다.
3. `package.json`에 Tailwind 관련 패키지가 빠져 있어 클래스가 전부 무시되고 있었다.

> **배운 점**: "코드가 그럴듯해 보인다"와 "실행 가능한 프로젝트 구조다"는 다른 문제입니다. AI가 짜준 컴포넌트 하나하나는 문법적으로 옳았지만, 그것들을 묶어주는 **진입점·번들러·설정 파일의 관계**를 이해하지 못하면 아무것도 동작하지 않는다는 걸 직접 겪고서야 체감했습니다.

### 2) 인증은 됐는데 글쓰기는 막힌다 — `Missing or insufficient permissions`

Firebase Authentication을 켜고 회원가입까지는 성공했습니다. 그런데 글을 발행하려 하면 `FirebaseError: Missing or insufficient permissions`가 떴습니다.

처음에는 "로그인이 덜 됐나?" 싶어서 로그인 로직을 의심했습니다. 하지만 콘솔 로그를 끝까지 추적해보니, **게시물 자체는 정상 생성되고 있었고**, 그 직후 작성자의 활동 카운터(`postCount`)를 올리는 두 번째 쓰기 작업에서 막히고 있었습니다.

원인은 Firestore Security Rules였습니다. 칭호 시스템이 클라이언트에서 위조되지 않도록 `users` 컬렉션의 수정 가능 필드를 `displayName`, `bio`, `photoURL`로만 엄격히 제한해뒀는데, 정작 게시물 작성 로직은 같은 문서의 `postCount`를 함께 올리려 시도하고 있었던 겁니다. **코드와 보안 규칙이 서로 다른 가정을 하고 있었던 것**입니다.

> **배운 점**: 보안 규칙은 "막아두면 안전하다"가 아니라 **애플리케이션이 실제로 하는 모든 쓰기 작업을 정확히 알고 그것만 허용**해야 의미가 있습니다. 프론트엔드 코드와 백엔드 규칙을 한 사람이 동시에 설계할 때는, 둘 사이의 계약을 명시적으로 맞춰보는 과정이 빠지면 반드시 어딘가에서 어긋난다는 걸 배웠습니다.

### 3) `CONFIGURATION_NOT_FOUND` — "켜져 있을 것이다"라는 가정이 틀렸을 때

Vercel에 처음 배포한 직후 구글 로그인을 누르면 `CONFIGURATION_NOT_FOUND` 에러가 떴습니다. API 키도, 환경변수도 맞게 넣었는데 왜 안 되는지 한참 헤맸습니다.

결국 원인은 단순했습니다 — Firebase 콘솔에서 **Authentication 자체를 "시작하기" 버튼으로 활성화한 적이 없었던 것**입니다. 키가 발급되어 있다고 해서 그 서비스가 켜져 있다는 뜻은 아니었습니다.

같은 패턴의 실수를 Firestore와 Storage에서도 한 번씩 더 겪었습니다(`allow read, write: if false`라는 기본 보안 규칙이 모든 읽기/쓰기를 차단하고 있던 것). 매번 "이미 설정했다고 생각했던 부분"이 실은 기본값 그대로였습니다.

> **배운 점**: 클라우드 서비스는 "만들면 바로 켜진다"가 아니라 **기능마다 명시적으로 활성화하고, 권한을 명시적으로 열어줘야 동작**합니다. 로컬 개발 환경에서는 보이지 않던 이 단계가, 배포 환경에서는 그대로 장애 지점이 된다는 걸 직접 막혀봐야 알 수 있었습니다.

### 4) 재배포는 매번 새로 만드는 게 아니라는 것

코드를 고칠 때마다 Vercel 프로젝트를 새로 만들어야 하는 줄 알았습니다. 실제로는 `git push` 한 번이면 Vercel이 변경을 자동 감지해서 같은 URL에 덮어쓰기 배포한다는 걸 알게 된 후, 수정 → 커밋 → 푸시 → 자동 반영의 흐름이 손에 붙기 시작했습니다.

## 이 과정에서 깨달은 것 — "AI로 짠다"와 "개발한다"의 차이

AI는 코드를 매우 빠르게, 문법적으로 정확하게 만들어줍니다. 하지만 이번 프로젝트에서 실제로 막혔던 지점들은 전부 **코드 바깥**에 있었습니다.

- 파일들이 어떤 순서로 서로를 호출하는지(번들러 진입점)
- 클라이언트 코드와 서버 보안 규칙이 같은 데이터 모델을 가정하고 있는지
- 클라우드 콘솔에서 무엇을 "명시적으로" 켜야 하는지
- 에러 메시지 한 줄(`CONFIGURATION_NOT_FOUND`, `Missing or insufficient permissions`)을 읽고 그것이 정확히 어느 계층(인증/DB/스토리지/규칙)의 문제인지 좁혀나가는 진단 능력
- firebase , vercel , 등등 개발에 필요한 요소들을 만져보지 않고 단지 ai가 해주는 한 줄 설명으로 ~을 하라는 것을 이해하기는 어렵다. 고로 많은 경험을 쌓아 나아가야 한다.

이건 AI가 대신 겪어줄 수 없는 부분이었습니다. AI에게 "왜 안 되는지" 물어보기 전에, 먼저 **에러 메시지를 읽고, 가설을 세우고, 한 가지씩 소거하며 원인을 좁히는 과정**을 제가 직접 따라가야 했습니다. 이번 프로젝트를 통해 제가 키우고 싶은 역량이 명확해졌습니다 — AI가 만들어준 코드를 그대로 신뢰하지 않고, **왜 이렇게 동작하는지 끝까지 따라가서 검증하는 습관**입니다.

## 프로젝트 구조

```
src/
├── firebase/firebase.js     # Firebase 초기화 (.env 기반, 키 하드코딩 금지)
├── context/AuthContext.jsx  # 전역 인증 상태
├── hooks/useFollow.js       # 팔로우/언팔로우 로직
├── utils/
│   ├── badges.js            # 칭호 조건 계산
│   └── uploadMedia.js       # UUID 기반 중복 방지 업로드
├── components/
│   ├── BadgeTag.jsx
│   ├── PostEditor.jsx       # 텍스트 퍼스트 글쓰기
│   └── PostDetail.jsx       # 리액션 · 댓글 · 스포일러 블라인드
└── pages/
    ├── HomePage.jsx
    ├── LoginPage.jsx
    ├── WritePage.jsx
    └── PostPage.jsx
```
